# ANIME VOID 17 — подключение аккаунтов и оплаты

**Сейчас реальные платежи выключены.** Обычная загрузка файлов на GitHub Pages включает локальную мастерскую, но не запускает Python, базу или приём денег. Здесь рабочая серверная реализация, не уже подключённая касса и не юридическое заключение. До денежных операций нужны развёртывание, проверка на тестовом магазине ЮKassa, настройка чеков/документов и независимая проверка безопасности.

## Что разработано
- Аккаунты с логином/паролем, одноразово показываемым кодом восстановления, сменой пароля через код и отзывом сессий.
- SQLite: баланс заработанных осколков, одноразовые награды, инвентарь, настройки, история и заказы. Пароли — scrypt N=131072/r=8/p=1 с солью; токены и коды восстановления хранятся хешированными.
- Версия и URL принятых условий фиксируются на сервере при регистрации и создании заказа. При изменении документов обновляйте `TERMS_VERSION`. Это техническая запись согласия, не юридическая экспертиза самих документов.
- Цена и состав покупки берутся из серверного `profile-catalog.json`, не из присланного браузером баланса/цены. SQLite-транзакции не допускают двойного списания. Заказ резервирует пересекающиеся предметы до завершения проверки.
- ЮKassa: создание redirect-платежа, idempotence key, проверка платежа GET-запросом, сравнение суммы/RUB/получателя/test-mode/заказа/аккаунта. Факт перехода на return_url ничего не выдаёт.
- Повторные уведомления не дублируют выдачу. Полный подтверждённый возврат снимает только соответствующее платное право; независимая покупка за осколки не удаляется. Частичный возврат — `refund_review`, требует оператора. Возвраты денег оформляются в кабинете ЮKassa; сервер обрабатывает результат, не заменяет поддержку.
- Авторская рамка только аккаунту с UUID из `OWNER_ACCOUNT_ID`. Логин «author», локальный бэкап или присланный `role` такой роли не дают.

## Ограничения, которые нельзя скрывать
1. Отметки серий — самоотчёт пользователя, **не доказательство просмотра**. Сервер вычисляет награды по присланному прогрессу, дедуплицирует серии/достижения и ограничивает начисление, но не может доказать просмотр видео на стороннем сайте. Часы/жанры тоже приходят из локального каталога. Редактирование всего трекера может накручивать бесплатные награды. Осколки не продаются, не выводятся, не переводятся и не конвертируются в деньги.
2. Локальный магазин и серверный аккаунт независимы. Не импортируйте локальный баланс или инвентарь в серверную БД. Пользователь может учесть свою историю в аккаунте, но это заново обрабатывается серверными правилами и таблицей claims. Денежные покупки подтверждаются исключительно платёжным API.
3. Местные списки просмотра остаются в браузере. Аккаунт синхронизирует оформление/инвентарь/награды, **не весь трекер**. Для серверного оформления нужен доступ к API. При недоступном API показан локальный профиль с предупреждением.
4. У сессии срок 7 дней; в браузере токен в sessionStorage, не в обычном бэкапе. Код восстановления показывается при регистрации/сбросе. Потеря и пароля, и кода требует ручной проверки владельцем; автоматического email-сброса нет.
5. Нет подписок, автоплатежей, сохранения карт, переводов пользователям, лутбоксов или продажи валюты. Деньги покупают конкретное оформление по указанной цене.
6. Исходники интеграции протестированы на локальном имитаторе API. Реальный тестовый магазин/боевые списания не проверялись: нет ключей владельца. Нельзя объявлять систему аудированной или уже соответствующей всем законам.

## Что необходимо владельцу в России
- Подходящий подтверждённый магазин ЮKassa. Сам факт наличия сайта или DonationAlerts не даёт подключения кассы. ЮKassa указывает возможность подключения для самозанятых, ИП и организаций: [1](https://yookassa.ru/questions/q66/). Провайдер должен одобрить деятельность и товары.
- Определиться с налоговым статусом, чеками и допустимостью продажи цифрового оформления. Указать реальные контакты продавца, оферту/условия аккаунта, конфиденциальность, порядок возврата. Учесть требования к персональным данным и месту их хранения. При необходимости — профильный юрист/бухгалтер. Договоры и регистрация оператора не создаются этим кодом.
- Linux-сервер с Python 3.11+, постоянным диском и HTTPS-доменом для API. Рекомендуется от 1 GB RAM, особенно из-за scrypt; не увеличивайте число рабочих процессов без оценки памяти. SQLite нельзя хранить на исчезающем диске бесплатного контейнера.
- Ключи, базу, email покупателей и резервные копии хранить **на отдельном сервере, не в репозитории GitHub Pages**. Frontend остаётся на `https://anime-void-app.github.io/AV/`.

## 1. Развернуть API — схема для Linux/VPS
Эти команды выполняются **на сервере**, не в файле сайта и не в браузерной консоли. Нужны права администратора. Примеры путей из `anime-void-studio.service` должны совпасть с реальными.

1. Создайте системного пользователя `avstudio`, директории `/opt/anime-void-studio/backend` и `/var/lib/anime-void-studio`, выдайте их пользователю `avstudio`.
2. На сервер скопируйте папку `backend` и **рядом с ней** `profile-catalog.json` из этого выпуска. Каталог сервера и каталог frontend должны быть одинаковыми. Перед любым изменением цен сделайте бэкап и не меняйте состав уже созданных заказов.
3. Из `/opt/anime-void-studio` создайте окружение и установите production HTTP-сервер:

```bash
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
```

4. Скопируйте `backend/.env.example` в `/etc/anime-void-studio.env`, задайте владельца `avstudio` и права `600`. Этот файл не коммитьте. `ALLOWED_ORIGINS=https://anime-void-app.github.io` — **без `/AV/`**, потому что Origin не содержит путь.
5. Сначала оставьте `REAL_PAYMENTS_ENABLED=0`. Заполните рабочие HTTPS-ссылки `TERMS_URL`, `PRIVACY_URL`, имя продавца и контакты; иначе регистрация в production не включится. `PAYMENT_MODE=test`, БД — отдельная тестовая.
6. Установите предоставленный systemd unit, затем:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now anime-void-studio
sudo systemctl status anime-void-studio
```

7. Настройте Caddy по `Caddyfile.example`: замените домен, направьте DNS на сервер. Gunicorn слушает только `127.0.0.1:8128`, наружу открываются HTTPS/443 и порт получения сертификата. Не открывайте 8128 в интернет. Caddy должен перезаписывать `X-Forwarded-For` и `X-Forwarded-Proto`, а не принимать их как истину от клиента.
8. `TRUST_PROXY=1` + `TRUSTED_PROXY_IPS=127.0.0.1/32,::1/128` подходят для этой native-схемы. Для контейнеров/другого прокси укажите **точные доверенные адреса**. Не ставьте `0.0.0.0/0`.
9. Проверьте `https://ВАШ_API_ДОМЕН/api/health`: должен быть JSON с `ok: true`. `/api/config` не должен раскрывать секретов; при выключенной кассе показывает `paymentsEnabled: false`.
10. В frontend-файле `studio-config.js` заполните только `apiBase: "https://ВАШ_API_ДОМЕН"`, затем Commit → Sync. Приватных ключей в этом файле быть не должно. После изменения конфигурации обновите PWA с интернетом.

`python server.py` / ThreadingHTTPServer предназначен для локальной разработки. В интернете используйте Gunicorn/WSGI за HTTPS reverse proxy. Для локальной проверки без настоящих платежей установите `APP_ENV=development`, отдельный `DB_PATH`, разрешите `http://localhost:...`; это не production-настройка.

## 2. Подключить тестовый магазин ЮKassa

Официальные материалы:
- Начало: https://yookassa.ru/developers/payment-acceptance/getting-started/quick-start
- HTTP-уведомления и проверка подлинности: https://yookassa.ru/developers/using-api/webhooks
- API: https://yookassa.ru/developers/api

1. Войдите в кабинет ЮKassa и создайте/подключите **тестовый магазин**. Найдите идентификатор магазина и API-ключ в разделе интеграции/ключей. Интерфейс кабинета может отличаться — ориентируйтесь на официальную инструкцию для вашего магазина.
2. Только на сервере заполните `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`. Не присылайте секрет в чат, не кладите в `studio-config.js` и не делайте Commit с ним.
3. Создайте случайный секрет уведомлений длиной не менее 32 символов, например:

```bash
python3 -c 'import secrets; print(secrets.token_urlsafe(40))'
```

4. Запишите его в `WEBHOOK_SECRET`. URL уведомлений:
   `https://ВАШ_API_ДОМЕН/api/payments/webhook/ВАШ_СЕКРЕТ`
5. В кабинете в настройке HTTP-уведомлений укажите этот URL и события `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Сервер не доверяет данным уведомления о сумме или статусе: перепроверяет объект через API с ключом магазина.
6. Настройте чековый сценарий и реквизиты. `RECEIPT_MODE=provider` отправляет email, позицию, сумму, НДС и признак предмета расчёта в платёжный запрос. Это работает **только при фактически подключённом и правильно настроенном фискальном решении**. Значения `RECEIPT_VAT_CODE` и `RECEIPT_SUBJECT` нельзя выбирать наугад.
7. `RECEIPT_MODE=external` разрешён только если у вас уже есть отдельно реализованный и проверенный обязательный чековый процесс. Код не создаёт чек в «Мой налог» и не заменяет ККТ сам по себе.
8. После проверки чеков, поддержки и юридических HTTPS-страниц задайте `FISCAL_READY=1`, `REAL_PAYMENTS_ENABLED=1`, **оставив `PAYMENT_MODE=test`**. Это включит только тестовый сценарий. Перезапустите сервис.
9. Зарегистрируйте тестовый аккаунт сайта, сохраните recovery-код, купите оформление тестовым способом из документации провайдера. На сайте должна быть явная отметка ТЕСТ. Проверьте: ожидание не выдаёт предмет; успешный платёж выдаёт; повторная проверка не дублирует; отмена не выдаёт; возврат снимает оплаченное право; другой аккаунт не видит чужие заказы.

## 3. Перейти к реальным операциям — отдельный этап

Только после тестов собственного магазина, проверки условий подключения, чеков, документов, доступности поддержки, TLS, резервного копирования и независимого ревью безопасности:
- отдельные рабочие ключи магазина;
- `PAYMENT_MODE=live` и **новый `DB_PATH` для рабочей БД**;
- живые webhook и return URL;
- продуманный порядок миграции аккаунтов: тестовые балансы и платные права **не переносить** в рабочую базу;
- `FISCAL_READY=1`, `REAL_PAYMENTS_ENABLED=1`.

Код откажется запускать одну БД то как test, то как live. Проверка `payment.test` также запрещает смешивание. Это предохраняет от превращения тестовых оплат в реальные права, но не заменяет настройки провайдера.

## 4. Назначить авторскую рамку

1. Создайте свой настоящий аккаунт на настроенном сервере. Сохраните код восстановления.
2. На сервере загрузите тот же защищённый environment и из папки backend выполните:

```bash
python manage.py account ВАШ_ЛОГИН
```

3. Полученный `id` запишите в `OWNER_ACCOUNT_ID` серверного env и перезапустите сервис. Другим пользователям эту переменную не выдавайте.
4. Перезайдите в мастерскую: появятся авторская отметка и рамка «Автор ANIME VOID». Имя аккаунта само по себе ничего не доказывает.

## 5. Обслуживание, возвраты, данные

- `manage.py` сам читает `/etc/anime-void-studio.env` (можно изменить через `AV_ENV_FILE`), не исполняя его как shell. Запускайте от пользователя `avstudio`; он должен иметь доступ к env и базе. Без существующего `DB_PATH` команда откажется работать, чтобы не создать ложный пустой бэкап.
- Ежедневно делайте консистентную копию SQLite командой `python manage.py backup /ЗАЩИЩЁННЫЙ_ПУТЬ/backup.sqlite3`. Храните зашифрованную внешнюю копию отдельно; проверяйте восстановление. Не копируйте только основной .sqlite3 во время работы, игнорируя WAL.
- Поставьте `python manage.py reconcile` на запуск раз в 5 минут от сервисного пользователя с тем же env: он перепроверяет ожидающие заказы, в том числе после пропущенного webhook. `python manage.py review` показывает возвраты/заказы, которым нужен оператор. Один запуск обрабатывает до 100 ожидающих заказов.
- Если создание запроса зависло, повтор используется с тем же UUID/idempotence key. Заказы без полученного payment_id старше 23 часов требуют ручной проверки в ЮKassa: повторно создавать оплату вслепую нельзя.
- Полный возврат оформляйте через кабинет провайдера; дождитесь уведомления и проверьте отзыв предмета. Частичные возвраты/chargeback/спорные списания требуют ручной обработки и поддержки. Здесь нет полноценной бухгалтерии или отдельного административного веб-кабинета.
- База содержит логин, хеши пароля/кода/сессий, историю наград, отслеженные ID серий, метрики и заказы; **email для чека сохраняется в заказе** для устойчивого повтора запроса. Данных карт нет. Укажите это в политике и определите законные сроки хранения/удаления, включая финансовые записи и резервные копии. Запросы на удаление аккаунта обрабатывает оператор: автоматического удаления финансовой истории нет.
- IP хранится как SHA-256 в таблице ограничений запросов. Тело платежей, пароль и секрет webhook API не логируются. Настройте proxy-логи так, чтобы секретный путь уведомлений и персональные данные не попадали в публичные логи. Очищайте старые rate-лимит записи по собственной политике; их удаление сбрасывает только лимиты, не награды.
- Доступ к серверу — SSH-ключи, обновления, firewall, защищённый env и регулярное наблюдение за ошибками. Настройте внешнее ограничение запросов при росте нагрузки. Авторизацию стоит дополнительно проверить аудитом перед реальными деньгами.

## Проверка разработки
Локальные HTTP/браузерные тесты включали подмену цены, неподтверждённое уведомление, неверные test-mode/сумму/аккаунт, параллельное списание, повторный callback, полный refund, сессии/recovery и авторскую роль. Использовался **имитатор провайдера**, не реквизиты настоящего магазина. Развёртывание, действующие платежи и фискализация владельца не выполнялись.
