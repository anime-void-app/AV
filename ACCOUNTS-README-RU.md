# ANIME VOID24.5 — аккаунты и приватная облачная копия

## Статус: реализация подготовлена, не объявлять уже подключённой

Добавлены `account.html`, общий клиент `av-account.js`, регистрация/вход по почте, восстановление пароля и Google OAuth через Supabase PKCE. Кнопки входа профиля и сообщества ведут на новую страницу. Вход использует существующий проект и существующий ключ сессии `avSupabaseAuthV1`, не создаёт второй каталог пользователей.

**В рабочую БД SQL не применялся. Google Cloud и провайдер Google не настроены агентом. Реальные Google-вход, доставка писем, продакшен-сохранение и Windows/мобильные браузеры владельца не проверены.** Публичная проверка настроек Supabase при подготовке: email включён; Google выключен. Нужны следующие действия владельца. Не вставляйте сервисный ключ или OAuth secret в JS, GitHub, чат или настройки публичного сайта.

Старый Python/SQLite backend из предыдущих выпусков не участвует в этой схеме. Оставьте `studio-config.js → apiBase` пустым, чтобы не создавать параллельную систему аккаунтов.

## 0. Сначала HTTPS и резервные копии

На `http://animevoid.ru` новые вход и синхронизация намеренно заблокированы. Нужно исправить DNS/сертификат и включить GitHub Pages Enforce HTTPS. Пока DNS-серверы Timeweb возвращают лишнюю AAAA, следуйте инструкции поддержки регистратора. Не отключайте браузерные проверки сертификата.

Перед публикацией скачайте локальный бэкап из старого профиля на каждом устройстве, где есть важные данные. Сделайте резервную копию БД/существующих настроек Supabase доступным способом. **Не удаляйте старые auth.users, таблицы VIP/автора/подарков, не запускайте повторную выдачу подарка всем.**

## 1. Подключить облачную БД

Откройте https://supabase.com/dashboard и **существующий** проект, чей URL:

`https://bszukonnqdujllmblwcw.supabase.co`

Слева **SQL Editor → New query**. Вставьте содержимое `ACCOUNT-CLOUD-SETUP.sql`, нажмите **Run**. Скрипт транзакционный и добавочный: две новые таблицы, RLS и одна функция записи. Старые пользователи, публичные профили, DM, подарки и гранты не меняются.

- `av_account_documents`: последняя приватная копия владельца;
- `av_account_document_history`: три предыдущие версии;
- `av_account_save`: запись с проверкой ожидаемой версии. UID владельца берётся из `auth.uid()`. Параметр `p_expected_user` только сверяет, что сессия не сменилась во время запроса; выбрать чужого владельца им нельзя;
- анонимам доступ закрыт; прямые INSERT/UPDATE/DELETE роли authenticated запрещены; SELECT через RLS только своей записи;
- лимит документа12MiB, ограничение числа ключей и типов. Это резервная копия личного app state, **не таблица покупок/финансовых прав**.

При ошибке остановитесь и проверьте сообщение. Не отключайте RLS ради устранения ошибки. Скрипт идемпотентно проверен в изолированном PostgreSQL17 с имитированными auth.users/auth.uid, не в рабочем проекте.

## 2. URL входа и email

В Supabase откройте **Authentication → URL Configuration**:

- Site URL: `https://animevoid.ru`
- Redirect URLs: `https://animevoid.ru/account.html`
- Если реально используете www, добавьте `https://www.animevoid.ru/account.html` после исправления его HTTPS.
- Если используете ещё GitHub-подпуть, добавьте точный адрес его `account.html`. Не используйте широкие wildcard на посторонние домены.

В **Authentication → Sign In / Providers → Email** оставьте включёнными email/password и подтверждение почты. Настройте минимальный пароль12символов в серверных security settings: проверка формы не заменяет серверные правила.

Для регистрации обычных посетителей настройте **свой SMTP** в Supabase. Встроенная тестовая почта может иметь ограничения получателей/частоты. Проверяйте реальную доставку confirmation/recovery, папку Spam и сроки действия ссылок. Используется PKCE: confirmation/recovery ссылку нужно открывать в том же браузере/профиле, где начат процесс. Если verifier утрачен, начните запрос заново, не переходите на небезопасный implicit-поток.

## 3. Google

В Google Cloud Console:

1. Создайте/выберите свой проект.
2. Настройте Google Auth Platform / OAuth consent: имя приложения, контактные адреса, аудитория, домен, действующие privacy/terms URL. Если приложение в Testing, добавьте разрешённых тестовых пользователей. Для широкой аудитории завершите необходимую публикацию/проверку Google.
3. Создайте OAuth client типа **Web application**.
4. В **Authorized redirect URIs** вставьте именно callback **Supabase**, а не index.html сайта:

   `https://bszukonnqdujllmblwcw.supabase.co/auth/v1/callback`

5. В Supabase **Authentication → Sign In / Providers → Google** включите провайдер, вставьте Client ID и Client secret из Google Cloud и сохраните.
6. Секрет хранится только в настройке провайдера Supabase. На сайт он не нужен.

Для прежнего аккаунта сначала войдите прежним способом и проверьте его UUID. Не переносите VIP/автора по совпадению отображаемого имени или неподтверждённой почты. Не создавайте новый аккаунт ради обхода проблемы связывания. Автоматическое связывание идентичностей выполняет Supabase по своим правилам, не наш JS. Отдельный интерфейс ручного linking/unlinking в этом этапе не добавлен.

## 4. Публикация: после входа всё автоматически

Загрузите содержимое папки «САЙТ» на GitHub Pages/хостинг после исправления HTTPS и настройки Supabase. SW: `av-AV-core-v24.29`.

- Кнопка **«Аккаунт»** есть в профиле и в боковой панели главной. Это один раздел: **Аккаунт / Настройки / Сохранение / Безопасность**. Тема, масштаб и комфорт открывают настоящие настройки, не макет.
- Войдите существующим аккаунтом: подключать устройство и нажимать «Сохранить» не нужно.
- Если у аккаунта ещё нет облачной копии и локальные данные не привязаны к другому UID, существующий прогресс этого браузера автоматически отправляется в аккаунт. На общем устройстве проверьте, чьи это старые, ещё не привязанные данные: система не может установить их исторического владельца.
- Если облачная копия уже есть, она автоматически загружается. Страница перезагружается сама, чтобы старые виджеты не продолжали работать со старым состоянием.
- Данные, уже привязанные к другому UID, не загружаются в новый аккаунт. Перед сменой сохраняется локальная страховочная копия в IndexedDB. Новый пустой аккаунт получает пустое состояние, а не чужой инвентарь.
- Правки пользователя запускают сохранение с задержкой около200ms; фоновая проверка изменений — каждые3секунды. Дождитесь статуса **«Сохранено»** перед очисткой данных браузера/уходом на другое устройство.
- При сетевой ошибке изменения остаются в localStorage и резервной очереди IndexedDB. При возвращении связи включается повторная проверка аккаунта и отправка. Повторы имеют задержку3–60секунд. «Нет связи» не выдаётся за успешное облачное сохранение.
- Независимые изменения разных ключей автоматически объединяются по общей версии. Избранное/серии объединяются с учётом добавлений и удалений. Настоящий конфликт одного поля не разрешается случайным выбором: обе копии сохраняются и показывается статус конфликта. Автоматическое слияние кошельков не выполняется.
- Для редких конфликтов есть **«Сохранение → Дополнительно и восстановление»**: выбрать версию, скачать текущую копию, последние локальные изменения или копию до восстановления. Кнопок подключения и «Сохранить сейчас» в обычном сценарии нет. Прежние3серверные версии также сохраняются.

При возврате к прежнему UID его неотправленные изменения автоматически продолжают отправку, если серверная версия не успела измениться. При сложном конфликте остаются резервные копии своего UID в дополнительных настройках. Чужой UID в интерфейсе восстановления выбрать нельзя. Локальные копии не зашифрованы от владельца устройства/DevTools; IndexedDB — не защита от физического доступа.

Файлы книг/видео не загружаются. Локальные данные на другом домене/в другом профиле браузера не видны автоматически. Не очищайте браузерное хранилище при несохранённых изменениях. В режиме приватности/при недостатке места IndexedDB может быть недоступен: синхронизация сообщит об ошибке, а не будет удалять данные ради продолжения.

Выход отзывает локальную сессию, но оставляет данные на устройстве. На общем компьютере после подтверждения облачного сохранения очистите данные сайта. Перед ручным восстановлением закройте другие вкладки с редакторами. Техническое переключение аккаунтов не заменяет отдельные профили браузера для разных людей.

## Что реально покрыто / что ещё предстоит

Сохраняется валидируемая локальная копия AVSafe: списки, статусы, серии, рейтинги, избранное, коллекции, заметки/цитаты, чтение/закладки, настройки интерфейса, выбранное оформление и локальные изображения в поддерживаемом формате. Не все данные сайта находятся в localStorage: исходные файлы книг, произвольные файлы устройства, видео, пароли и сессии не копируются. Серверные посты/DM/публичные аватары остаются в прежней серверной системе. Ключи вне AVSafe, включая отдельный авторский `avAuthorStyle:<uid>`, в эту копию не входят. Отдельного экрана восстановления старой истории ещё нет; три версии доступны владельцу через Supabase.

**Кошелёк/инвентарь сохраняются как непроверенный пользовательский архив. Это НЕ завершённый защищённый серверный кошелёк.** Для полного переноса денег/покупок нужен следующий этап: транзакционный ledger, серверные правила начислений/цен и миграция подтверждённых прав. Клиентский JSON не должен быть доказательством оплаты или основанием для серверного VIP/автора/модерации. В этом этапе не добавляются реальные платежи, удаление аккаунта, произвольная загрузка файлов в облако, автоматическое объединение разных аккаунтов или ручное связывание провайдеров.

Ранее выданные серверные авторские/VIP/персональные гранты и SQL восстановления **не менялись и не запускались повторно**. Первый вход автоматически переносит старые ещё не привязанные локальные данные только в новый пустой аккаунт. Импорт чужого/поддельного файла не должен выдавать серверные права.

Для публичного запуска нужны актуальные условия и политика обработки данных/согласия; техническая форма не является юридической проверкой или гарантией соответствия законам.
